## 3. Investigation Objective
The objective is to prepare a review-ready investigation plan for the Nitro warning:

`inlineDynamicImports option is ignored because the codeSplitting option is specified.`

The future investigation must answer the following technical questions without changing the repository configuration:
- What is the origin of `inlineDynamicImports` in the effective build pipeline?
- What is the effective Nitro configuration produced by the shared wrapper?
- Why is `codeSplitting` specified simultaneously with an ignored `inlineDynamicImports` option?
- Is the ignored option intentional, or does it indicate a configuration mismatch or a wrapper-behavior mismatch?
- What evidence would demonstrate the expected Cloudflare module output and runtime behavior?

## 4. Existing Evidence Baseline
The following evidence is recorded and must be used as the baseline for this proposal:

- Current repository configuration: [`vite.config.ts`](../../vite.config.ts) imports `@lovable.dev/vite-tanstack-config` and comments that the wrapper supplies Nitro using a Cloudflare default target. The file overrides the TanStack Start server entry but does not show the effective Nitro configuration object.
- Current package metadata: [`package.json`](../../package.json) declares `nitro` in `devDependencies` and `@lovable.dev/vite-tanstack-config` in `devDependencies`.
- B-11K owner disposition: W-03 is assigned `UNDETERMINED` and `REQUEST ADDITIONAL INVESTIGATION`.
- B-11G D-06: requires every build warning to be reviewed and assigned a documented disposition. It does not authorize configuration change or implementation by itself.
- B-11J notes the build passed but the warning was not dispositioned and that no runtime or deployment verification was performed.

Known limitations:
- Repository-owned configuration does not establish the effective Nitro config as produced by the shared wrapper.
- The checked-in files do not prove whether `inlineDynamicImports` is intentionally ignored or whether it is a mismatch caused by wrapper behavior.
- The recorded build output demonstrates only that the build completed and emitted the warning; it does not prove runtime behavior in Cloudflare or a deployed environment.
- This proposal does not infer effective Nitro configuration solely from repository-owned config when wrapper internals have not been inspected.

## 5. Questions to Be Answered
1. Where does the `inlineDynamicImports` option originate, and why is it present in the effective config path?
2. What is the effective Nitro configuration generated by `@lovable.dev/vite-tanstack-config` in the current project and evaluated version?
3. Why does the warning state that `inlineDynamicImports` is ignored when `codeSplitting` is already specified?
4. Is the ignored option an intentional no-op, or does it suggest that the wrapper and Nitro options are not aligned?
5. What evidence would demonstrate the expected Cloudflare module output and runtime behavior without shipping to production or authorizing a config change?

## 6. Proposed Investigation Scope
The future investigation, if separately approved, should be limited to the following read-only tasks:
- Trace the effective Vite/Nitro config as produced by the wrapper rather than inferring it solely from repository-owned config.
- Compare wrapper-supplied Nitro options with the semantically relevant Vite/Nitro settings for `codeSplitting` and `inlineDynamicImports`.
- Determine whether the warning is the result of intentional configuration semantics or a mismatch between wrapper and underlying Nitro behavior.
- Identify what evidence would be needed to validate expected Cloudflare module output and runtime behavior in a non-production setting.
- Document the known limitations before any eventual owner disposition under D-06.

This scope excludes deployment, production runtime verification, and any change to Nitro, Vite, TanStack, or Cloudflare configuration.

## 9. Expected Evidence and Verification Criteria
A future investigation should produce:
- A precise origin statement for `inlineDynamicImports` and its relation to the wrapper-generated config.
- A documented effective Nitro configuration derived from the wrapper and underlying package behavior.
- An explanation of why `codeSplitting` and `inlineDynamicImports` are simultaneously present, and why the warning says the latter is ignored.
- A statement of whether the ignored option appears intentional or as a configuration mismatch.
- A set of evidence items that would demonstrate expected Cloudflare module output and runtime behavior without production deployment.

The evidence must support a later owner disposition under D-06 without assuming the warning is harmless or material.

## 10. Verification and Acceptance Criteria
A future investigation should be considered complete only when the following are documented:
- The origin and effective value of `inlineDynamicImports` are identified and traced to the wrapper or underlying package.
- The effective Nitro config is described in a way that distinguishes repository-owned config from wrapper-generated config.
- The relationship between `inlineDynamicImports` and `codeSplitting` is explained with direct evidence, not inference.
- The evidence required to validate Cloudflare module output and runtime behavior is explicitly listed.
- The record distinguishes between actual configuration semantics and unverified runtime assumptions.

Static inspection of repository configuration and wrapper source may establish a configuration-generation path, but it does not automatically prove the exact effective Nitro configuration used by the build pipeline. Any effective configuration value that cannot be directly established from available evidence must be reported as UNVERIFIED.

Static inspection can establish configuration declarations, wrapper code paths, and documented build-target settings when supporting source is available. It cannot independently establish actual Cloudflare module output or runtime behavior. Any build-based, runtime, or deployment verification requirement must be identified separately and submitted for explicit Project Owner authorization.

Acceptance means the evidence is sufficient for a later owner disposition under D-06. It does not imply any configuration change is approved.
